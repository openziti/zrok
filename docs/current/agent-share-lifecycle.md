# Agent share lifecycle

Public requests from the CLI and agent use the same preparation rules for proxy, web, Caddy and drive backends. Port-only targets retain their HTTP interpretation, with port 443 using HTTPS. File targets become absolute in the invoking CLI before being sent to the agent; a direct agent request resolves relative paths in the agent's environment. Preparation copies selections, credentials, access grants and OAuth patterns, leaving the caller's request unchanged. Basic authentication and OAuth are mutually exclusive. A basic authentication entry is split at its first colon, so a username cannot contain a colon and a password can; this is the split the frontends apply to the `Authorization` header. An entry with no colon is refused. No validation error quotes an entry: the CLI names the source (the position among `--basic-auth` values, or stdin) and refuses with exit 2, and preparation, the backstop for callers that bypass the CLI, names the entry's position. The Go, Node and Python SDKs apply the same grammar when they build a share request. OAuth patterns must compile, and the agent parses a supplied refresh duration before starting a worker; an omitted duration uses three hours.

An omitted or empty list of agent name selections uses the current default namespace at preparation time, parsed with the CLI's `namespace[:name]` rules: `team` leaves name allocation to the controller, while `team:app` selects namespace `team` and name `app`. The agent process's nonempty `ZROK2_DEFAULT_NAMESPACE` wins, followed by the current nonempty `default_namespace` in the original root's `config.json`, then `public`. Missing configuration uses the fallback; malformed or unreadable configuration fails the request when the file is needed. Explicit selections bypass this read and retain their supplied values; a selection with an empty or blank namespace fails preparation instead of falling back to a default. Refreshing the namespace changes neither the cached environment nor the credentials used for operations. Prepared selections remain fixed for that attempt, while saved requests retain their original intent for later preparation.

`share public` takes basic authentication users from one of three mutually exclusive sources, none of which can be combined with `--oauth-provider`: `--basic-auth <username:password>` (repeatable), `--basic-auth-from-stdin` (one entry, the first line of stdin) and `--basic-auth-file <path>`. The file holds one `username:password` per line. Either line ending is accepted, and blank or whitespace-only lines are skipped. There is no comment syntax, since a username or password may begin with any character. Each entry follows the grammar above, and whitespace around the username and the password is trimmed. A file over one mebibyte (1048576 bytes) is refused, and the refusal states that limit. A file that yields no entries, a missing or unreadable path and a directory are refused. Every refusal names the path, and a malformed entry also names its line number; none quotes the line. Whether the flag was given is decided by whether it was set, never by its value, so `--basic-auth-file ""` (an unset variable, usually) is refused with exit 2 before environment loading and agent routing rather than read as the flag being absent. zrok does not inspect the file's permissions.

`--basic-auth` and stdin are value sources: the credentials themselves become the request. The file is a reference source: the request carries a path, and the users are read from it when a share is created, by whichever process creates it. In standalone execution the CLI makes the path absolute, reads the file once before the share is created, and creates the share with its entries; any refusal exits 2 with nothing created.

Routed to an agent, the CLI makes the path absolute, exactly as for a file target, and sends it in `basicAuthFile` with no users. It does not read the file; the agent is the only reader, so the question of which contents created a share has one answer. The agent's saved request carries the path in place of credentials, and that request is at once what the agent registers, compares for identity, reports and saves: two requests that differ only in the contents of the file they name are the same request. A direct gateway request may carry the path too; a relative path there resolves in the agent's environment, as file targets do, and a path combined with users or an OAuth provider is refused, since a direct request bypasses the CLI's flag exclusivity. On the wire an empty path cannot be told from an absent one, so the agent reads an empty path as no reference; refusing an empty path is the CLI's job, where the flag's presence is known.

The agent reads the file on every attempt to create the share: the original request, replay at startup, and a retry after a failed start or an unexpected worker exit. The users go into the prepared request handed to the create and nowhere else. They are not kept on the running share, not reported in status, and not logged. Reading at every create is what makes rotation work: the agent deletes a managed public share at shutdown and creates a fresh one at start, so a changed file takes effect the next time the share is created, and not on a share that is already running.

At the original request a file problem refuses before anything is created. The agent answers with gRPC `InvalidArgument` carrying the reader's message, which the CLI classifies as permanent: exit 2, as standalone. Only the reader's errors and the conflicting-sources refusal cross this way; other preparation errors keep their classification. At replay or retry there is no caller to refuse. The failure is an ordinary failed start: recorded on the operation, shown in status with the path, and retried under the existing policy, and the request keeps its restart intent, so a file that appears late (a slow secret mount) brings the share up on a later attempt. At no point does a file problem produce a share without authentication.

Standalone public execution creates the share, starts its backend, then stops the backend and deletes the share on signal, TUI exit, startup failure or unexpected serving completion. Backend execution contains no controller create/delete calls. Caddy startup runs inline; proxy and drive serve in a goroutine and report unexpected completion to the command. A backend constructed after stop was requested is stopped without serving. Deletion failures are returned with the share token.

The agent creates each managed public share using its original environment and credentials before launching a worker. It records the returned token and public endpoints in the registered operation. The worker runs `share public --subordinate --share-token <token>` with only backend mode, insecure setting and normalized target; names, authentication, permissions and access grants stay with the agent. Worker readiness must match the supplied token and cannot replace the controller's token or endpoints. Public `--share-token` is hidden and requires `--subordinate`, including when the flag was explicitly supplied empty. A subordinate requires a nonblank token and refuses `--basic-auth-from-stdin` and `--basic-auth-file`; a worker's stdin is the agent's control channel, and a worker takes no authentication input. Invalid combinations fail before stdin is read, environment loading or agent routing. Private token options retain their existing behavior.

The CLI checks its release series before routing to an agent, so it will route to an agent from an earlier release of the series. An agent declares what it understands beyond its series in the `capabilities` of its version response. Before sending an entry whose password contains a colon, the CLI requires `basic-auth-first-colon`; an earlier agent splits at every colon and would reject the entry and quote it. Without the capability the CLI refuses with exit 2, names the agent's reported version and says to restart the agent, and sends nothing. Before sending a file reference it requires `basic-auth-file`, a separate capability, because an earlier agent ignores a request field it does not know and would create the share with no authentication; the refusal is the same. The checks run when the share is sent, not at detection, so `--force-agent` does not skip them. An entry with exactly one colon goes to any agent.

Public create failures carry the controller's HTTP status, error message and busy retry interval through structured agent RPC error details. The CLI preserves exit 2 for controller refusals (4xx except 429), and exit 1 for 429 and 5xx responses. Backend failures and pending-cleanup errors remain separate from create refusals, retaining their diagnostics and known cleanup tokens.

Every agent child now has one process reaper. `Done` and `WaitChild` report the actual process exit independently of output callbacks; `DrainWaitDone` reports either completed output delivery or expiry of the one-second post-exit drain allowance. A blocked logging callback may outlive that allowance, so `DrainWaitDone` does not guarantee the callback has returned. Reader chunks own their bytes, including data delivered with EOF, and closed output channels are removed from the combiner.

The controlled public-worker launch path supplies a parent-owned stdin pipe and separates protocol stdout from diagnostic stderr. Closing that pipe requests graceful stop. The stop helper waits five seconds, force-kills if necessary, then allows five more seconds to confirm exit; a cancelled wait or unconfirmed exit returns an error. POSIX controlled workers use a process group for forced termination; Windows retains job assignment and suspended-process activation, with kill and reap on activation failure. These durations and the drain allowance are injectable in tests.

The backend-only worker runner registers EOF and terminal signal handling before backend construction, stops a late backend installation, and returns serving failures. Its strict public boot handler verifies the supplied token without replacing parent-owned identity or endpoints. The newline parser retains partial lines, skips blanks and processes coalesced messages, with a one-MiB line limit. EOF before boot or a line overflow fails startup when the controlled stdout-close callback is connected. Private and access boot field mappings remain unchanged.

Managed public workers use the controlled launch, backend-only runner and strict readiness path. They never create or delete controller shares, including on startup failure or stdin EOF. Private and access workers continue through the legacy launch interface, with shared process completion and repaired framing.

The agent registers each operation before starting its worker and makes lifecycle decisions under one mutex. Startup, active state, cleanup, retry and release refer to that same operation. External work, including process waits, controller calls, health checks and registry writes, runs outside the mutex. Status and registry responses contain independent copies of mutable request data. Cleanup callers share one attempt; a failed attempt retains the resource identity and can be retried. Recreation waits for successful cleanup, and cleanup remains eligible after explicit release has removed restart intent.

Worker startup waits for boot, process exit, caller cancellation or a six-minute deadline. Public creation has a separate 60-second bound, including client initialization and version checking. Once dispatched, creation settles within that bound even if the caller cancels or shutdown begins; a returned token is recorded and cleaned up without reporting readiness. Once startup succeeds, the original caller's context no longer governs the running worker. Legacy private and access workers retain force-stop behavior and their resource policy: a supplied private token survives ordinary shutdown, while explicit release retains its deletion behavior.

The agent registry stores desired restart requests across active, stopping and retry states. Successful eligible requests and every imported request keep their intent through ordinary shutdown; a new request that fails before success gains no restart intent. Explicit release removes intent before waiting for cleanup. All entries are imported before replay starts, so shutdown or a release during replay preserves the unattempted remainder. Caller starts and releases, including direct agent methods, wait outside the lifecycle mutex for import before admission, then recheck shutdown and caller cancellation. This wait does not include worker replay. A caller starting a matching queued request uses its imported restart intent rather than creating a duplicate. If import fails, saves fail without replacing the unread file. A dedicated write mutex serializes fresh snapshots, and an atomic file replacement avoids partially written registries. Retry scheduling is cancelled and joined during shutdown, and an in-flight retry keeps its failure ID until its result has been accepted or drained.

A saved public request holds a file reference as `basic_auth_file` with an empty `basic_auth`; the users it names are never written to the registry. The agent reads registry version 2 or 3 and refuses any other version. Every save writes version 3, whatever the registry holds. A version 2 file is read as it is, without conversion; the save at the end of startup replay writes it as version 3, so upgrading needs no manual step. The version does not depend on the contents because agents from earlier releases refuse any version but 2 and never replay a refused registry, and that refusal is the only protection a downgrade has. Those agents ignore `basic_auth_file`, so one that replayed a file reference would create the share with no authentication. They also split an entry at every colon, so one that replayed a saved password containing a colon would reject it and quote it in a failure it persists to the registry and reports through status.

Rolling back to an earlier release is therefore a manual edit for everyone. `v2.0.8` and `v2.0.9` both refuse a version 3 registry and create nothing from it, but they treat the file differently: `v2.0.9` leaves it unread and unreplaced, so it can be edited afterwards, while `v2.0.8` logs the refusal, continues with an empty registry and overwrites the file at its next save, so for `v2.0.8` the edit has to come before that agent starts. These reactions are established by reading those releases, not by running them. The edit, in this order: remove every public share entry that has a `basic_auth_file`, and every one whose `basic_auth` holds a password containing a colon, then set `v` to `"2"`. The order matters because the version is the guard. An entry with a file reference left behind in a file marked version 2 matters most: the earlier agent creates that share with no authentication at all. A colon password left behind is quoted in a persisted failure.

Shutdown closes admission at the operation boundary, cancels startup and retry dispatch, drains registered work concurrently, and saves a final registry snapshot. Local, remote and gateway servers retain their listeners and receive graceful stop with force-stop fallback; a listener created after shutdown begins is closed without registration. Repeated shutdown calls join one shared result. The overall allowance is 120 seconds. Failure or expiry reports incomplete cleanup and known tokens and makes the agent command exit 1; successful joined shutdown exits 0. A fatal startup error follows the same cleanup path.

After public worker exit is confirmed, the agent deletes every managed public share, including named shares. Reserved names and desired restart requests survive ordinary shutdown. An unconfirmed worker exit retains the token without deleting its resource. Public deletion uses a fresh 30-second context shared by client initialization, version checking, deletion and any absence check. A typed unshare-not-found response is reconciled through the generated authenticated account overview: the original environment must be present and the token must be absent from every environment. Generic errors, a missing environment, a still-listed token or a failed overview retain the cleanup failure. Context-aware SDK entry points require a root with bounded client initialization; legacy SDK entry points keep supporting the original root interface.

Cleanup failures remain visible with the real token, failed status and a pending-cleanup error. Retry backoff applies to deletion before recreation; cleanup remains retryable after explicit release removes restart intent. Startup errors include any cleanup failure and known token. Shutdown attempts outstanding cleanup and reports unresolved tokens on failure. Pending cleanup identities remain in memory, not in the registry. An agent crash, a lost create response or a restart after failed shutdown can require manual cleanup; existing live-share name conflicts still return the controller's actionable 409 without evicting another share. Native platform validation is recorded below.

## Deliberate boundaries

Private shares and accesses retain legacy creation ownership, including their unknown-token startup window; migrating them requires a separate scope decision, and access workers must still discover their local bind address. Public attachment by token remains subordinate-only until a standalone ownership contract is designed. The registry does not recover known cleanup obligations across restart; durable recovery needs a migration and a surviving-worker policy. Ambiguous creates without a returned token need controller-supported request identification or reconciliation.

Basic authentication from a file has these accepted limits. A named share created through the agent from a value source (`--basic-auth` or stdin) still saves its credentials in the registry, because a value has nowhere else to live across a restart; the file is the answer for anyone who needs the registry clean. The agent does not watch the file and does not update a running share's users: a live share keeps the users it was created with until it is released or the agent restarts, since changing them is an update to the share, which the agent does not do for any property. The controller's remote share API does not carry a file reference: a path names a file on the agent's host, and that API is spoken from somewhere else. It still forwards basic authentication entries to an enrolled agent as received; an agent from an earlier release rejects and quotes a password containing a colon sent that way, and the controller logs the rejection, which is existing behavior this work neither causes nor changes. zrok does not inspect the file's permissions, since secret mounts are commonly world-readable inside their container and Windows has no equivalent check. The file is not an htpasswd file and holds no hashed passwords; users are stored in the share's frontend configuration and compared as supplied. The file is read as UTF-8 text: a byte-order mark is not stripped and UTF-16 is not decoded. A leading mark becomes part of the first username, and a UTF-16 file is either refused as malformed or yields users no client can supply; neither creates a share without authentication. The drive commands' `--basic-auth` (`copy`, `ls`, `md`, `mv`, `rm`) is a client credential for someone else's WebDAV server, keeps its old split and does not quote the value in its error. The agent console's share form offers no basic authentication.

The agent does not infer authority to evict a live holder from a name conflict. Controller leases and orphan collection would change server resource lifetimes. Removing worker processes would require addressing Caddy's process-global lifecycle. These remain separate designs; none is required for the implemented orderly public cleanup path.

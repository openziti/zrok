# 2026-10-02

- `zrok2 admin gc` decides ownership by the `zrokShareToken` tag and never by name. v2 policy names lead with the environment ZId (`<envZId>-<shrZId>-bind`, `<envZId>-<token>-serp`, `<feToken>-<envZId>-<shrZId>-dial`), so any name parsing marks every live share's policies orphaned; that is how the old gc stripped a live private share on dev. An object with no share token is not gc's (agent-remote, frontend, dynamic proxy controller objects) and is counted, never deleted.
- A ziti list with limit zero returns the default page of ten, not everything. `automation.FindAll` pages at `MaxPageSize` (500). `GetByName` and `GetByID` still send a zero limit, which is harmless for name and id lookups. The fake now pages the same way, so a test seeding more than ten objects of a kind and reading them through a zero-limit `Find` sees ten.
- `DeleteWithFilter` (and so `CleanupByTag`, the Ziti step of `teardownShare`) now lists through `FindAll` before deleting; before step 12 it read one page of ten, so a share with more than ten objects of one kind was torn down with the rest left behind. It must list everything first: deleting while paging by offset shifts later objects into pages already read.
- gc deletes policies and configs before services so that a failure part-way never leaves a policy or config pointing at a deleted service; a leftover service with no policies is harmless and the next run takes it.
- gc reads the live share set before listing Ziti, and the age guard is what covers a share whose objects exist before its row commits. Don't reorder the two reads or default `--min-age` to zero.
- Step 6 (relax for v2 public shares): `frontend_selection` is v1's column; v2 never writes it. A public share's desired dial policy comes from its live name mappings (namespace frontends), never from the share row; the row's selection is consulted only when there are no live mappings. Relax and `admin repair-dial-policies` share `desiredDialPolicies`, so a new policy kind added at create time needs adding there or both will miss it.
- `admin repair-dial-policies` must honour the bandwidth limit journal or it un-limits limited accounts: limitAction deletes dial policies and nothing else, so "missing dial policy" is exactly what a limited share looks like. It treats a `limit` entry whose limit class has no backend mode as whole-account limited, which is stricter than relaxAction's `limitedBackends` (that map ignores unscoped classes); deliberate.
- `influxReader.runQueryForRxTx` checks `result.Err()` after iterating. Without it, a deadline hit while reading the result ended `Next()` early and returned zero usage with no error, which relax reads as "under the limit".
- The relax fixture's "bad" share now fails through `zitifake.RejectCreates` on its dial policy name; a public share with no mappings and no selection now relaxes successfully, so it can no longer stand in for a failing share.
- A v1-shaped share whose `frontend_selection` names no live frontend is a per-share relax failure (`missingPublicFrontendError`, journal retained, cycle continues), not a store failure: a no-rows lookup aborts no PostgreSQL transaction, so ending the cycle for it stalled every account behind it. Any other lookup error stays a store failure. `admin repair-dial-policies` treats it the same way: the share is listed under failed shares with the frontend it selects, counted in `failed` (so the run exits non-zero), and the run continues; its access policies are not checked in that run, since the derivation stops at the error.

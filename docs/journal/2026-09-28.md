# 2026-09-28

- Share-create compensation deletes the objects the request recorded, by ID, and never calls `CleanupByTag`. `checkPrivateShareTokenAvailability` is a read before the create, so two requests for the same private token can both pass it; both carry the same `zrokShareToken` tag, and a tag-scoped cleanup by the loser would delete the winner's config, service and policies. Tag-scoped cleanup stays only where a share row already owns the token (unshare, disable, gc). `controller/access.go` has the same leak on its dial policy and is meant to reuse `zitiCompensation`.
- In real Ziti config names are unique too, so the private-token loser normally fails at the config create with nothing to compensate; the handler race test seeds the winner's service and policies without a config so the loser gets one object in before conflicting.
- `automation.IsNotFound` matches a fixed list of generated `Delete*NotFound` types: the pinned edge-api (v0.26.48) generates no `Code()` accessor, so there is no status to test. A new delete path in the package adds its type to the list, or its not-found will propagate as a failure.
- The generated edge-api errors format their payload as pointers (`createServiceBadRequest &{Error:0x...}`), so every manager call site wraps through `wrapEdgeError`, which unwraps the `APIErrorEnvelope` into `ziti <code>: <message> (cause: ...)` at the manager boundary. It wraps rather than replaces: `IsNotFound` and callers' `errors.As` match the generated type, so it has to stay in the chain. A new edge-api call in the package uses the helper, or its failures log without Ziti's message.
- The `shadow` analyzer is deliberately not in the vet gate: 163 findings tree-wide on `main`, nearly all the ordinary `if err := f(); err != nil` idiom. The share handler's lost allocation error is guarded by the restructure (no `:=` of `err` inside the mode switch) and the handler tests.
- `sessionCache.get` skips the CA fetch for a plain `http://` endpoint, which is what lets controller handler tests use `zitifake` through the production `NewZitiAutomation`. The session tests now run against a TLS fake (`zitifake.NewTLSWithCredentials`) so their CA-fetch assertions still cover the https path.

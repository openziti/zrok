# 2026-10-06

- Step 13: the name repair is the `admin repair-names` command, never a startup migration. A migration runs unattended at controller start, as one unbatched transaction against production PostgreSQL, with no dry run to review first. The sweep needs a reviewed dry run and small batches, and it repairs past data rather than changing the schema, so it runs when operations choose.
- `FindFrontendMappingByFrontendTokenAndNameWithShareState` decides share state with `exists` over every share row carrying the token (live if any is live), not a left join. `shares_token_idx` is unique only `where not deleted`, and private shares take user-chosen tokens, so a deleted and a live row can share a token; the old join returned an arbitrary one, and `healSeveredName` could remove a live share's frontend mapping. Any new query that maps a share token to share state needs the same shape.
- The three admin repair commands open the store through `openAdminStore`, which forces `DisableAutoMigration` on a copy of the config. A dry run must not change the schema either, and an operator running a newer binary against production would otherwise migrate it as a side effect. There is no schema check: a command fails only when a query hits a missing table or column. repair-names fails at once on a pre-v2 store; gc reads only `shares`, so it can run to completion against a behind store, which is harmless since it changes no rows there.

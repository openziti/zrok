# 2026-11-17

- An access whose frontend the controller had already removed could not finish cleanup or be released, in v2.0.9 and v2.0.10: the agent treated the controller's `unaccessNotFound` as a failed delete, so the operation stayed `failed` with its token and every retry or release repeated the same 404. The controller removes every access to a share when the share is torn down (`controller/teardownShare.go`), so this is the ordinary outcome of the sharing side going away, not an edge. Private shares had the same gap on `unshareNotFound`.
- The fix reconciles a typed not-found through the account overview, as public shares already did, and does not simply trust the 404: `controller/unaccess.go` also answers not-found when its own store delete of the frontend fails.
- Private share and access deletion from the agent now run under the 30-second cleanup context, through `sdk.DeleteShareContext` and the new `sdk.DeleteAccessContext`. They were unbounded before. This is deliberate: the delete and the absence check share one deadline, as on the public path. It is not the migration of private shares and accesses to agent-owned creation, which stays a separate decision.
- There is no way to clear a wedged access on an unfixed agent without restarting it, and a restart interrupts every share and access the agent runs.
- In the agent tests, wait for the delete to be observed before calling `cleanupDone`: the cleanup attempt does not exist until the monitor has claimed it, and `cleanupDone` dereferences it.
- The operator's reliable trigger for the stuck access is a port collision: `zrok2 access private -b <address>` through the agent, with the address already bound. The access worker creates the access, starts serving in a goroutine and reports ready at once; the bind then fails, the worker deletes its own access and exits, and the agent's cleanup deletes an access that is already gone. So the 404 comes from the worker and the agent both deleting, not only from a share being torn down.
- Not fixed, and separate: the access worker reports ready before it has bound (`cmd/zrok2/accessPrivate.go`). The command therefore reports success for an access that never binds, the access gains restart intent, and with the cleanup fix it now retries with backoff until the port frees or it is released. Binding before reporting ready would make the start fail with the bind error.
- The agent smoke scenario gained four steps between "start agent" and the public share: a private share, an access on a port the harness occupies, release of the access, release of the share. They assert the agent's settled state, never the access command's exit status, which depends on the race above. The offline fake has an `access-stuck` mode that behaves as v2.0.10 did, and the scenario fails on it. These steps have run only against the fake, on Linux.
- The offline harness suite now takes about twice as long, since most scenario tests run four more child processes; the workflow's bound for it went from 5 to 10 minutes. The fake's private share release uses its own path (`/fake/delete-private`), because `/fake/delete` is where the read-failure tests inject their failures.

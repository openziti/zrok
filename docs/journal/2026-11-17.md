# 2026-11-17

- An access whose frontend the controller had already removed could not finish cleanup or be released, in v2.0.9 and v2.0.10: the agent treated the controller's `unaccessNotFound` as a failed delete, so the operation stayed `failed` with its token and every retry or release repeated the same 404. The controller removes every access to a share when the share is torn down (`controller/teardownShare.go`), so this is the ordinary outcome of the sharing side going away, not an edge. Private shares had the same gap on `unshareNotFound`.
- The fix reconciles a typed not-found through the account overview, as public shares already did, and does not simply trust the 404: `controller/unaccess.go` also answers not-found when its own store delete of the frontend fails.
- Private share and access deletion from the agent now run under the 30-second cleanup context, through `sdk.DeleteShareContext` and the new `sdk.DeleteAccessContext`. They were unbounded before. This is deliberate: the delete and the absence check share one deadline, as on the public path. It is not the migration of private shares and accesses to agent-owned creation, which stays a separate decision.
- There is no way to clear a wedged access on an unfixed agent without restarting it, and a restart interrupts every share and access the agent runs.
- In the agent tests, wait for the delete to be observed before calling `cleanupDone`: the cleanup attempt does not exist until the monitor has claimed it, and `cleanupDone` dereferences it.

# 2026-09-26

- Round 4 supersedes the blanket best-effort enrichment disposition: confirmed not-found continues without retry (normal traffic for another service), while transient store errors retry then drop because acknowledging without attribution silently loses real share usage. Enrichment and durable writes now share one per-message deadline.
- Shutdown is not failed processing. Both the agent's drain and the source's cancelled send deliberately leave deliveries unsettled so the broker requeues them on connection close. The operator rejected Terminus's proposed shutdown nack because it would discard valid messages on restarts; the no-requeue rule applies to processing failures.
- Deadlines for `controller/limits/influxReader.go` are explicitly deferred by the operator to the relax stage. A stuck query can stall that worker, but the bounded handoff prevents it from parking the metrics consumer.
- Usage counters distinguish absent from mistyped: absent is zero for legitimate one-sided intervals; present-and-mistyped makes the event invalid.
- Operator vetoes for this stage: the bridge acknowledging a failed publish belongs on the route's filler track (publisher-side under-count, unable to fill the broker); environment disable bypassing shared share teardown belongs to a numbered later stage. Leave `bridge.go`, `amqpSink.go`, and `disable.go` untouched here.
- Ephemeral environments intentionally have a null account ID (migration 002); enrichment tolerates it, retaining share/environment attribution with account zero.
- The consumer isolates panics per message and drops the poison delivery without requeue, for the same reason as the relax cycle's isolation: one bad item must not crash controllers repeatedly through broker redelivery.
- Metrics consumer verified live against the dev RabbitMQ (Docker, `rabbitmqctl` inside the container) with InfluxDB pointed at a closed port and 300 synthetic `fabric.usage` events for a real share id. Pre-fix build: all 300 delivered and parked unacknowledged, `messages_ready` 0, none settled until the channel closed. Step 2 build (retry budget shortened to 5s for the run): `messages_unacknowledged` pinned at the prefetch of 64 throughout, ready draining as each message exhausted its budget and was nacked, all 300 dropped in about a minute, no panics, controller up. With Influx reachable, 100 events were acked and written within 5 seconds. Watch `messages_unacknowledged`; `messages_ready` reads 0 in the failure mode.
- A `make test` run does not refresh `GOBIN`; a live run of a working-tree change needs `go build` (or `make`) first, or it runs the previous install.
- Transient enrichment verified live: with a TCP relay between the controller and Postgres killed mid-run, events for a real share went through the bounded retry ("usage processing attempt '1' failed: ... connection refused") and were nacked without requeue ("message dropped"); with the relay restored the next events were enriched, written and acked; the controller stayed up throughout. The store's error through a dead relay is "connection refused" from `BeginContext`, never `sql.ErrNoRows`, so the not-found sentinel cannot misfire on an outage.
- `zrok2 --verbose` does not enable debug logging: `PersistentPreRun` in `cmd/zrok2/main.go` re-initialises `dl` at `slog.LevelInfo` when the flag is set. Pre-existing; not changed here.
- Ziti session refresh is guarded by generation rather than promising exact-once authentication: the goal is removing per-operation pressure on the shared authentication limiter, and occasional redundant refreshes are acceptable. The HTTP transport handles 401 so every manager and existing caller shares the same behavior, including replay of create bodies. Failed re-authentication or a persistent 401 propagates as the operation's typed error after at most one refresh/replay; it must never become a retry loop.

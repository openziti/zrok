# 2026-10-05

- Step 11: the share-create availability check now ignores dead mappings, and that switch cannot be separated from soft-deleting them. `share_name_mappings` has a partial unique index on `name_id where not deleted`, so a check that merely skips dead rows lets the request reach the mapping insert and turns the old 409 into a 500. `healSeveredName` does both in one routine for share create, `createShareName` and `deleteShareName`; a new name path calls it rather than querying mappings itself.
- `healSeveredName` is a repair, not a teardown. It must not grow OpenZiti calls or share-row deletes; anything that removes a share goes through `teardownShare`. It checks everything before modifying anything, so a conflict leaves the rows as they were even without the rollback.
- A frontend mapping whose share token matches no share row at all counts as a live holder (inherited from the old `healStaleFrontendMappings`), not as severed. That is why `TestShareFailedFrontendMappingInsertFailsRequest` no longer seeds an `other-token` row to make the insert fail: the check now answers that row with a 409 before the insert. The test makes the insert fail with a sqlite trigger instead.
- `createShareName` creates the name before calling `healSeveredName`, so the routine always receives a real name row; the new name has no share mappings, so only the frontend half does anything there, and a conflict rolls the name back.
- The auto-allocated branch of `processNameSelections` (no name given) does no healing, deliberately: its name is the fresh share token, so nothing can be severed on it. Its only change is that the not-granted refusal is now a typed conflict.
- `healSeveredName` returns one unbind per frontend mapping it removes (frontend token and name, like `teardownShare`). Share create puts them ahead of its binds in the one post-commit list. That order is what keeps the new share mapped, because unbind is by name only on the frontend (`endpoints/dynamicProxy/mappings.go`). An unbind published after the bind for the same name drops the new share's mapping. The name handlers publish their unbinds after their own commit.
- `processNameSelections` returns `*nameSelectionConflict` for the user-caused cases and a plain error otherwise; the share handler answers 409 only for the typed one (`errors.As`) and 500 for the rest. No-rows on the namespace or name lookup counts as user-caused (a 409, as before); a new user-facing refusal in that function must use the typed conflict, or it turns into a 500.
